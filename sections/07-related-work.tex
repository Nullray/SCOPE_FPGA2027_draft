\section{Related Work}
\label{sec:related}

\subsection{Modeled Systems and FPGA Services}

Model-based systems make component behavior and timing controllable. FireSim
provides FPGA-accelerated, cycle-exact simulation of scale-out systems
\cite{karandikar2018firesim}. FASED generates composable cache and DRAM models
whose target timing is decoupled from the FPGA host memory system
\cite{biancolin2019fased}. SimBricks composes host, device, and network
simulators through explicit interfaces and synchronized communication channels,
including configurations with existing NIC and switch RTL
\cite{li2022simbricks}. These systems support repeatable experiments with
modeled components, including driver workloads. Their evidence concerns the
behavior represented by the selected models. \sys instead focuses on functional
interaction between prototyped hardware, native drivers, and assigned physical
devices, complementing those controlled experiments.

Where model-based systems abstract component behavior, FPGA virtualization
abstracts the resources available to FPGA applications at the resource, node,
and multi-node levels~\cite{vaishnav2018survey}. Feniks factors common services
into an FPGA operating system and supports direct access to local PCIe resources and remote cloud
resources~\cite{zhang2017feniks}. FOS modularizes the FPGA system stack and
schedules elastic accelerator resources across dynamic workloads
\cite{vaishnav2020fos}. ViTAL decouples application compilation from runtime
resource allocation and virtualizes on-board DRAM and Ethernet
\cite{zha2020virtualizing}. Hetero-ViTAL extends this abstraction across
heterogeneous FPGA clusters~\cite{zha2021heterovital}. Coyote assembles
virtual memory, communication, networking, and spatial and temporal sharing into
a common FPGA execution environment~\cite{korolija2020coyote}.

Across these systems, the consumer is an FPGA application or tenant, and the
reassigned abstraction is fabric capacity or a shared service. \sys addresses
a different consumer: a processor DUT whose native drivers expect a peripheral
device contract. Physical-device virtualization is therefore a closer
comparison than virtualization of the FPGA resources themselves.

\subsection{Physical-Device Virtualization and Disaggregation}

FVM is the closest comparison at the device interface: it implements storage
virtualization on an FPGA and directly manages physical NVMe devices
\cite{kwon2020fvm}. Its combination of virtual presentation and physical
execution establishes that this design choice predates \sys. The distinction
lies in the consumer and the placement of mediation. FVM accelerates storage
virtualization for host virtual machines, whereas \sys presents a configurable peripheral
hierarchy to an FPGA-hosted processor DUT and keeps device-specific control
mediation in the host software back-end. This choice avoids an FPGA-resident
controller engine for each supported device protocol at the cost of software
control latency. The resulting resource benefit must be measured.

Rack-scale composable systems use PCIe switches to assemble physical compute,
memory, and I/O resources into workload-specific machines
\cite{li2017composable}. FlexForge disaggregates on-card memory and host-side
PCIe bandwidth from individual FPGA chips so those peripheral resources can be
allocated independently~\cite{lim2024flexforge}. Both approaches reassign
physical resources through a fabric. At the DUT boundary, \sys adds a logical
PCIe hierarchy and may adapt commands and DMA addresses before execution by the
assigned physical device. This presentation and mediation can complement a
composable fabric while relying on its transport and isolation mechanisms.

\subsection{The Processor-DUT Boundary}

\sysprevious~\cite{scope2026fpt} addresses peripheral borrowing across DUT and
host address domains. Its direct mode relies on SCOPE-aware DUT software, and
its proxy mode exposes a split-driver command interface for observation and
intervention. \sys inherits its routing, payload-path separation, semantic
adapters, and physical execution. Table~\ref{tab:related-boundaries} distinguishes
this inherited substrate from the native-driver-facing contract added here.

That contract exposes a logical PCIe hierarchy whose supported composition and
physical-device assignments are selected in host software. Native kernel drivers consume
the selected view through discovery and ordinary device operations, without a
SCOPE-specific command interface. Supporting these drivers requires
authoritative configuration and FPGA-visible routes to remain consistent with
the inherited execution path. Section~\ref{sec:design} develops commit points
for configuration retirement, physical submission, and completion publication
across their distinct state owners. These points preserve ordering required by
native protocols across the added presentation boundary.

The resulting distinction concerns the native contract consumed by a processor
DUT and its mediation in host software over a generic FPGA interface. \sys
goes beyond assigning a real device, while leaving compatible execution to that
device. The two decouplings in the system overview explain this partition, and
the commit points specify the visibility and ownership conditions that reconnect
the separated responsibilities. RDMA attachment extends these responsibilities
to a remote host while retaining the same DUT-facing contract; the transport
instantiates the method rather than defining its contribution.
