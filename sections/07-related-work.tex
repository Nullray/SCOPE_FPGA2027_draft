\section{Related Work}
\label{sec:related}

\subsection{Processor Prototyping and FPGA Services}

Model-based prototyping allows component behavior and timing to be configured.
RAMP Gold separates functional and timing models for FPGA-based full-system
simulation~\cite{tan2010rampgold}. FireSim
provides FPGA-accelerated, cycle-exact simulation of scale-out systems
\cite{karandikar2018firesim}. FASED generates composable cache and DRAM models
whose target timing is decoupled from the FPGA host memory system
\cite{biancolin2019fased}. SimBricks composes host, device, and network
simulators through explicit interfaces and synchronized communication channels,
including configurations with existing NIC and switch RTL
\cite{li2022simbricks}. These systems support repeatable driver and system
experiments with modeled components. \sys uses physical devices to test
functional interactions with prototyped hardware and native drivers.

Commercial prototyping also combines simulation with physical I/O.
Synopsys' DesignWare Hybrid IP Prototyping Kits combine Virtualizer processor
and memory models with HAPS-DX FPGA implementations of interface IP and
real-world connectivity~\cite{synopsys2015hybrid}. These kits support
pre-silicon software development and integration. \sys uses an FPGA-hosted
processor DUT whose software accesses host-attached devices through a
software-selected device view.

FPGA virtualization manages resources for FPGA applications at the resource,
node, and multi-node levels~\cite{vaishnav2018survey}. Feniks factors common services
into an FPGA operating system and supports direct access to local PCIe
resources and remote cloud resources~\cite{zhang2017feniks}. FOS and ViTAL
modularize system services and
separate applications from runtime resource allocation
\cite{vaishnav2020fos,zha2020virtualizing}; Hetero-ViTAL extends virtualization
across heterogeneous FPGA clusters~\cite{zha2021heterovital}. Coyote combines
virtual memory, communication, and sharing in a common FPGA execution
environment~\cite{korolija2020coyote}. At the storage interface, DONGLE 2.0
lets HLS kernels directly orchestrate NVMe access through a unified memory
and storage interface~\cite{wong2024dongle}.

These systems provide services to FPGA applications and tenants. \sys
targets the OS and drivers of a processor DUT, which discover peripherals
and issue operations through device protocols.

\subsection{Physical-Device Virtualization and Disaggregation}

Virtual I/O interfaces may follow an existing device protocol or introduce
virtualization-specific operations. Virtio standardizes virtual-device interfaces used by
guest drivers~\cite{russell2008virtio}. MDev-NVMe instead retains the native
guest NVMe driver through mediated pass-through and active
polling~\cite{peng2018mdev}. LeapIO exposes virtual NVMe storage to unmodified
guest VMs and offloads storage services to ARM SoCs using a unified address
space~\cite{li2020leapio}. These approaches combine software mediation with
guest-driver support in a host VM environment.

Device Lending makes a remote PCIe device appear local to an unmodified
driver~\cite{markussen2018lending}. It injects a device through emulated
hot-plug, maps its register regions through a non-transparent bridge (NTB),
and establishes reverse DMA and interrupt mappings. IOMMU-assisted DMA
translation connects the borrower's buffers to the lender's address domain.
SmartIO extends PCIe-based borrowing and sharing through distributed
shared-memory facilities while keeping software out of the payload
path~\cite{markussen2021smartio}. Remote placement can therefore remain
transparent to the driver while the assigned physical device executes
its operations.

Device Lending provides register, DMA, and interrupt mappings for a
borrowing host. \sys exposes a logical device hierarchy to an FPGA-hosted
processor DUT through a generic FPGA front-end. Host software maintains
logical configuration and endpoint state, and adapts commands and
address-bearing metadata before physical execution. The host and FPGA
coordinate configuration updates, prepared submissions, and completion
visibility through per-endpoint commit conditions.

FVM implements storage virtualization on an FPGA and directly manages physical
NVMe devices for host virtual machines~\cite{kwon2020fvm}. Zero2M places
tenant-level I/O management in an FPGA NVMe controller and uses namespaces to
identify tenants while retaining the native host storage
stack~\cite{wang2026zero2m}. Both place device-specific control in FPGA logic.
\sys keeps device-specific control mediation in host software and uses a
generic FPGA front-end to present endpoints to the processor DUT. The front-end
does not require a separate controller engine for each supported protocol,
although additional endpoints still consume configuration and routing
capacity. Host mediation adds control latency.

Rack-scale composable systems use PCIe switches to assemble physical compute,
memory, and I/O resources into workload-specific machines
\cite{li2017composable}. FlexForge disaggregates on-card memory and host-side
PCIe bandwidth from individual FPGA chips so those peripheral resources can be
allocated independently~\cite{lim2024flexforge}. Both approaches reassign
physical resources through a fabric. \sys can complement such fabrics by
constructing the DUT-visible device hierarchy and adapting commands and
DMA addresses before physical execution. This combination depends on
the transport and isolation mechanisms provided by the fabric.

\subsection{Peripheral Access for Processor DUTs}

\sysprevious~\cite{scope2026fpt} addresses peripheral borrowing across DUT and
host address domains. Its FPGA substrate remaps outgoing BAR accesses,
translates incoming DMA addresses, and regenerates DUT-visible interrupts.
Direct Control Mode routes mapped register operations in hardware and relies
on SCOPE-aware DUT software. Proxy Forwarding Mode exposes split-driver
commands to a host proxy for observation and replay. Device-specific semantic
adapters define submission, DMA, completion, and event behavior. This
substrate supports physical-device execution, address translation, and
local-host payload DMA without software copying. \sys adds the configuration
and state coordination needed for DUT OS enumeration and native-driver binding.

Host software selects the logical device hierarchy and physical-device
bindings in \sys. The tested Linux NVMe and Ethernet drivers discover and
operate their corresponding endpoints without modification or a
SCOPE-specific command interface. Accelerator workloads use adapted DUT
software. The host-owned
configuration, FPGA BAR routes, request metadata, and completion state
must remain consistent with physical execution. Section~\ref{sec:coherence}
specifies the corresponding commit conditions.
