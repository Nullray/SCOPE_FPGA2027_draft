\section{Introduction}
\label{sec:intro}

FPGA-based processor prototyping supports validation of hardware together with
system software before silicon is available. Running a production operating
system and its native drivers exercises a design under test (DUT) through
end-to-end workloads. Connecting real peripherals extends these workloads to
functional interaction with independently implemented devices, allowing
hardware--software integration to be tested beyond the chosen device models.
Prior FPGA and hybrid prototypes use physical I/O interaction for SoC functional
validation and integrated software testing~\cite{feng2018accelerator,callanan2011prototyping}.
% <!--ref:feng2018accelerator--><!--anchor:section:5,page:10-->
% <!--ref:callanan2011prototyping--><!--anchor:abstract-->
This complements controlled model-based experiments; it does not guarantee
complete behavioral coverage or silicon-equivalent timing. Its usefulness also
depends on which device configurations the prototype can present to software.

With direct attachment, device composition follows the available peripherals
and their placement. Supporting another device type may also require
device-specific FPGA logic and a new build. Moving devices to a host can relax
placement constraints, but remote reachability does not itself supply the
behavior expected by an unmodified driver. The challenge is to make the
DUT-visible peripheral subsystem configurable while retaining compatible
physical execution and the native-driver contract.

This paper asks: \emph{Can the logical device hierarchy consumed by native
drivers be selected in software independently of physical-device attachment?}
We present \sys, a software-defined peripheral subsystem whose \emph{goal} is
to make supported logical composition and compatible physical-device assignment
software choices. Host configuration selects the hierarchy and its exposed
contracts before enumeration, within provisioned FPGA capacity, without
changing the DUT driver or bitstream.

The software-defined principle is inspired by software-defined networking
(SDN), which separates applications, programmable control, and packet
forwarding~\cite{onf2014architecture}. Figure~\ref{fig:planes} uses that
organization to compare functional roles. SDN applications request network
behavior; in \sys, native drivers instead consume a device hierarchy selected
by host software. The FPGA front-end presents that hierarchy, while compatible
physical devices execute I/O involving DUT memory. Because the driver expects
one stateful device, this division must keep configuration, direct memory
access (DMA), completion, and interrupt behavior coherent across the joint
FPGA--host control tier. The analogy concerns the separation of
responsibilities, not equivalent programming interfaces or timing.

Two decouplings provide the architectural \emph{means} of achieving this goal.
\emph{Logical presentation--physical device decoupling} makes the supported
device hierarchy and its physical-device assignment independently selectable.
\emph{Control-semantics--data-path decoupling} permits mediation of that view
without forcing payload bytes through software. A generic FPGA front-end
presents the selected interface, while the host software back-end owns logical
state and device-specific control mediation. This division distributes state
that must still behave as one device to the native driver. \sys coordinates
configuration with routing, translated work with physical submission, and
returned data with completion at three per-endpoint commit points.

These responsibilities extend across host boundaries without changing the
contract consumed by the DUT. The local software back-end retains logical
authority and selects the device's location, while a remote software back-end
mediates execution at the assigned host. Remote direct memory access (RDMA)
provides one realization of that attachment. Its role is to instantiate
location-extensible peripheral access,
not to introduce a new RDMA protocol or require a transparent device-bus
extension.

\sysprevious~\cite{scope2026fpt} supplies the underlying peripheral-borrowing
substrate, including control/data separation, semantic adapters, and physical
execution. \sys adds a software-selected logical hierarchy consumed by native
kernel drivers, rather than a SCOPE-specific DUT interface. Its contribution
is to coordinate that configurable presentation with the inherited execution
path across distinct state owners.

This paper makes three contributions:
\begin{itemize}[leftmargin=*]
    \item It defines a native-driver-facing device abstraction in which
    supported logical composition and compatible physical-device assignment,
    including device location, are host software choices within a fixed FPGA
    interface capacity.
    \item It develops a coordination protocol at the configuration, submission,
    and completion boundaries, stating when the native driver or physical
    device may rely on distributed state under explicit memory-visibility
    assumptions.
    \item It demonstrates native-driver operation on a processor FPGA prototype
    with real NVMe and Ethernet devices in separate endpoint configurations.
    These functional tests are distinguished from inherited control-path and
    interrupt measurements, with matched data-path and capacity-scaling
    experiments identified as pending.
\end{itemize}

The study targets pre-silicon processor prototyping; post-silicon reuse remains
future work. Section~\ref{sec:motivation} compares peripheral-access
organizations and derives the requirements, while Section~\ref{sec:related}
positions the work relative to FPGA virtualization, simulation, and resource
disaggregation. Section~\ref{sec:overview} develops the architectural
separation, and Section~\ref{sec:design} explains coordination at the commit
points. Section~\ref{sec:evaluation} reports native-driver compatibility and
prototype costs within the current evidence boundary, followed by the
configurability--fidelity discussion in Section~\ref{sec:discussion}.
