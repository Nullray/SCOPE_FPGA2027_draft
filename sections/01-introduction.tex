\section{Introduction}
\label{sec:intro}

FPGA prototypes allow hardware and system software to evolve before silicon is
available. Their value increasingly depends on running a complete software
stack, including the operating system, production drivers, and realistic I/O
workloads. FPGA-accelerated platforms use timing-faithful component models and
modular simulation to make full-system experiments tractable
\cite{karandikar2018firesim,biancolin2019fased,li2022simbricks}. Real NVMe SSDs
and NICs complement model-based validation: software device models are configurable and observable, but their usefulness is
bounded by the fidelity of the modeled controller, firmware, timing, and DMA
behavior.

Attaching a real device retains its controller and firmware as participants in
validation, but usually makes the
validation environment rigid. The DUT can use only devices reachable through
the prototype board and its host topology. In platforms with hardware peripheral
proxies, adding device types can require device-specific RTL for configuration,
register access, DMA, and interrupts.
Changing the device composition may require rewiring, additional PCIe hardware,
or a new FPGA build. These costs consume both scarce FPGA resources and
engineering time, a concern also identified by FPGA operating-system work that
factors reusable I/O services out of application logic~\cite{zhang2017feniks}.
We call their incremental cost the \tax.

Moving a device to another host does not by itself remove this coupling. A DUT
does not consume an abstract remote-I/O service. Its unmodified Linux stack
expects a locally discoverable PCIe function with coherent configuration and
BAR state. Its driver creates protocol-specific queues, publishes DMA addresses,
rings doorbells, and assumes that data is visible before a completion or
interrupt arrives. Forwarding MMIO operations without preserving this end-to-end
contract may enumerate a device but cannot make it usable.

This paper asks: \emph{Can the peripheral subsystem visible to an FPGA-hosted
DUT be defined in software, without moving complete device implementations into
the FPGA and without changing the DUT driver?} We answer with \sys. Its goal is
\emph{software-defined peripheral access}: before DUT enumeration, host
configuration selects which provisioned logical endpoints are active, the
supported contracts they expose, and their bindings to compatible physical devices,
without requiring a new FPGA bitstream or DUT driver. This goal does not imply
arbitrary device protocols: the FPGA supplies generic interface mechanisms,
while the host software back-end must implement the advertised control semantics
and connect each endpoint to a suitable physical device.

Figure~\ref{fig:design-space} separates the device visible to the DUT, the
owner of control semantics, and the entity executing I/O. Virtualization gives
the user control over presentation and physical-device assignment.
Compatible physical execution retains an independent controller and firmware
for the operations exercised by the workload. \sys combines these properties
through selective control mediation. The exposed contract must remain
supported by the assigned device, and mediation can alter timing and
concurrency. Configurability, functional compatibility, and timing fidelity
are therefore distinct properties of the resulting validation environment.

The architectural means is \emph{dual decoupling}. Logical presentation--physical
device decoupling makes the supported view and compatible binding configurable.
Control-semantics--data-path decoupling permits semantic mediation without
forcing payload bytes through software. A generic FPGA front-end presents the
selected interface, and a host software back-end owns logical state and
device-specific mediation. Their distributed state must still behave as one
device to the driver. \sys coordinates it at three per-endpoint commit points:
configuration-write retirement after image and route installation, physical
submission after translated-state visibility, and completion publication
after data visibility.

\sysprevious~\cite{scope2026fpt} already provides cross-domain peripheral
borrowing, control/data separation, and semantic adapters. \sys extends that
substrate with a software-selected logical PCIe view consumed by native kernel
drivers. This interface adds configuration and routing authority to the
borrowed execution path, requiring their commit to remain consistent with
submission and completion. Native protocols already impose the underlying
ordering requirements. The contribution is the coordination of that contract
across the front-end, software back-end, and physical device, rather than
control/data separation or address translation alone.

This paper makes three contributions:
\begin{itemize}[leftmargin=*]
    \item It defines a native-driver-facing device abstraction in which
    supported logical composition and compatible physical-device binding are
    host software choices within a fixed FPGA interface capacity.
    \item It presents a coordination protocol that joins authoritative logical
    state and FPGA-visible configuration and routes to the inherited execution
    path. Per-endpoint commit points identify when a configuration access may
    retire, physical work may be submitted, and completion may be published,
    with explicit assumptions on memory visibility.
    \item It demonstrates the design on a processor FPGA prototype with real
    NVMe and Intel Ethernet devices, and evaluates native-driver operation in
    separate endpoint configurations while distinguishing it from inherited
    control-path and interrupt measurements.
    Matched data-path and capacity-scaling experiments are specified as pending.
\end{itemize}

The current implementation targets pre-silicon processor prototyping. The same
logical abstraction may be useful in post-silicon validation, but we treat that
extension as future work rather than a demonstrated contribution.
