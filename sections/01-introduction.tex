\section{Introduction}
\label{sec:intro}

FPGA-based prototyping of open-source processors supports validation of
hardware together with system software before silicon is available. Running
an operating system and its native drivers exercises a design
under test (DUT) through end-to-end workloads. Physical peripherals support
validation of interactions among the DUT, its software stack, and real devices.
Prior FPGA and hybrid prototypes have used such physical I/O interaction for
SoC functional validation and integrated software
testing~\cite{feng2018accelerator,callanan2011prototyping}.
% <!--ref:feng2018accelerator--><!--anchor:section:5,page:10-->
% <!--ref:callanan2011prototyping--><!--anchor:abstract-->
These tests complement controlled model-based experiments. Their scope
depends on which device configurations the prototype can present to software.

With direct attachment, device composition follows the available peripherals
and their placement. Supporting another device type may also require
device-specific FPGA logic and a new physical interface. Moving devices to a host can relax
placement constraints, but remote reachability does not supply the
behavior expected by an unmodified driver. The challenge is to make the
DUT-visible peripheral subsystem configurable while preserving the discovery,
control, and data-transfer behavior expected by native software stack.

\sysprevious~\cite{scope2026fpt} illustrates the distinction between reaching
a physical device and presenting it to the DUT OS. It provides cross-domain
register routing, semantic adapters, and a separate payload path. Its direct
mode uses SCOPE-aware base address register (BAR) mappings, while its proxy
mode carries split-driver
commands. Both use explicit DUT interfaces for access to the borrowed
peripheral. Extending this substrate to native-driver operation requires a
software-selected logical device hierarchy that the DUT OS can enumerate.
The configuration and operational state exposed to its drivers must remain consistent
with physical execution across the FPGA and host software.

This paper asks: \emph{How can an FPGA processor prototype expose a
software-selected logical device hierarchy to native drivers while coordinating
execution by physical devices in separate address domains?}
We present \sys, which provides software-defined peripherals for processor
prototyping. Before enumeration, the host configures the DUT-visible device
hierarchy and binds each logical endpoint to a physical device.
Once the corresponding device contracts are supported,
the hierarchy and backend assignments can be reconfigured without modifying either the DUT drivers or the FPGA bitstream.

Figure~\ref{fig:design-space} compares device modeling, direct attachment,
\sysprevious's peripheral borrowing, and \sys through three aligned roles:
DUT software, access abstraction, and execution resource. The key distinction
is the device view consumed by the DUT, rather than physical borrowing alone.
The separation of software configuration from controlled execution is inspired
by software-defined networking (SDN)~\cite{onf2014architecture};
Section~\ref{sec:sdn-principle} develops that architectural correspondence.

The architecture separates logical presentation from the assignment of
physical devices, and control mediation from payload movement. These separations
allow software to configure the device view while local-host payload DMA
bypasses software copying. A generic FPGA
front-end presents the selected interface, while the host software back-end
owns logical state and device-specific control mediation. This distribution
requires explicit coordination: configuration must agree with routing,
translated work must be visible before physical submission, and returned
data must be visible before logical completion. \sys expresses these
dependencies as three per-endpoint commit conditions.

\sys also supports access to peripherals attached to remote hosts.
Remote direct memory access (RDMA) provides transport between the local and
remote software back-ends. The local back-end maintains the DUT-visible
device state, while the remote back-end mediates physical-device execution.
Requests and data transfers across host address domains follow the same
commit conditions.

This paper makes three contributions:
\begin{itemize}[leftmargin=*]
    \item It introduces a native-driver-facing peripheral abstraction that
    separates DUT-visible device presentation from physical-device assignment.
    Host software selects the
    logical device hierarchy and binds its endpoints to compatible physical
    devices on local or remote hosts.

    \item It specifies commit conditions for configuration--route coherence,
    submission--DMA coherence, and data--completion coherence. The conditions
    require updated configuration and routes to be installed before a
    configuration write completes, request metadata and required input data
    to be device-visible before submission, and returned data to be DUT-visible
    before completion is published.

    \item It implements an FPGA prototype supporting storage, networking,
    and accelerators, and demonstrates NVMe and Ethernet operation with
    unmodified Linux drivers. The evaluation quantifies DUT-observed control
    latency, NVMe throughput, and FPGA resource use, and examines
    device-specific adaptation and driver responses to injected faults.
\end{itemize}
