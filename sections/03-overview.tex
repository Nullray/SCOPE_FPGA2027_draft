\section{System Overview}
\label{sec:overview}

\subsection{Software-Defined Device Contract}

Software-defined peripheral access is the \emph{goal}: host software selects a
supported logical PCIe composition and binds its endpoints to compatible
physical devices before DUT enumeration. The native driver consumes the
resulting device contract without knowing the physical attachment. Selection
is bounded by provisioned FPGA capacity and the semantics supported end to
end; it does not imply arbitrary device protocols or online hotplug.

The \emph{means} are two decouplings with different roles.
\emph{Logical presentation--physical device decoupling} separates the contract
discovered by the DUT from the identity and placement of the assigned physical
device. It makes composition and binding software choices.
\emph{Control-semantics--data-path decoupling} separates operations that need
semantic mediation from payload movement. It permits a host-local DMA path
without software byte copying, but does not by itself make the device view
configurable. Table~\ref{tab:decoupling} summarizes these distinct consequences.

\midrule

A physical device supplies controller and firmware execution for compatible
operations; virtualization supplies the selected logical view. Retaining
physical execution does not reproduce direct-attachment timing, because
mediation changes when operations reach the controller. Section~\ref{sec:discussion}
develops this configurability--fidelity tradeoff. The demonstrated scope is
pre-silicon native-driver operation in separate endpoint configurations,
as reported in Section~\ref{sec:evaluation}.

\subsection{Division of Responsibility and the Three Planes}
\label{sec:planes}

The \emph{FPGA front-end} is the generic DUT-facing hardware that exposes the
selected PCIe view and transports accesses. The \emph{host software back-end}
is the host-resident software that owns logical device state, chooses physical
bindings, and mediates control. Within that software, a \emph{device-semantic
adapter} interprets a supported protocol, while an \emph{endpoint context}
holds the state and binding of one logical endpoint. The \emph{physical device}
is the assigned real controller, not the back-end.

Figure~\ref{fig:overview} relates these responsibilities across configuration
and runtime. Before enumeration, the back-end supplies the logical state and
bindings used by the front-end to present the hierarchy. During I/O, the
front-end delivers control events to the appropriate endpoint context and
adapter. The physical device executes compatible operations, with host-local
payload DMA following a separate path to DUT memory.

This division borrows SDN's separation of programmable control from data
movement~\cite{onf2014architecture}. Figure~\ref{fig:planes} compares the
functional planes. The \emph{software plane} in \sys contains the DUT OS and
native drivers. The \emph{control plane} spans both the FPGA front-end and host
software back-end, which jointly present the device view and coordinate its
state. The \emph{data plane} groups physical execution and DUT memory, whose
host-local payload exchange is distinct from semantic mediation.

\begin{figure}[t]
    \centering
    \includegraphics[width=\columnwidth]{figures/paper/sdn_planes_scope_v2.png}

    forwarding; \sys presents a stateful native-device contract. Its FPGA
    front-end and host software back-end share the control plane, and its data
    plane retains compatible physical execution. Analogous planes do not
    imply equivalent APIs, reconfiguration granularity, or timing.}
    \label{fig:planes}
    \Description{Two aligned three-plane stacks compare SDN applications,
    controller, and forwarding with SCOPE v2 native drivers, a joint FPGA
    and host-software control plane, and physical device plus DUT memory.}
\end{figure}

The important difference is the consumer's contract. An SDN application
requests network services from a controller that programs forwarding
behavior. A native DUT driver instead expects configuration, queues, memory
ownership, completions, and interrupts to behave as one device. The back-end
must therefore coordinate state across address domains, not merely select a
forwarding destination. The analogy concerns responsibility separation rather
than an SDN-style southbound interface or runtime topology programming.

Within the control plane, \emph{control virtualization} constructs the logical
view and mediates state that differs from the physical device.
\emph{Control passthrough} retains compatible physical execution after any
required address or protocol adaptation. Both can apply to one endpoint.
Passthrough here does not mean transparent forwarding of every register or
full PCIe function assignment. Payload DMA is an independent choice: it may
bypass software byte copying even when submission control is mediated.

\subsection{Distributed Device State and Commit Points}
\label{sec:coherence}

The two decouplings distribute a native-device contract across several state
owners. Native protocols already require publication before ownership transfer
and data visibility before completion. The architectural problem is to retain
those dependencies when logical state, translated metadata, and payload move
through different components. \sys organizes coordination around three
per-endpoint commit points:

\begin{description}[leftmargin=*,style=nextline]
    \item[Configuration--route coherence.] A configuration write retires only
    after the authoritative image, its FPGA-visible shadow, and any affected
    BAR route agree.
    \item[Submission--DMA coherence.] A physical doorbell transfers ownership
    only after published work has been observed and its translated state is
    visible in the physical device's address domain.
    \item[Data--completion coherence.] Completion becomes driver-visible only
    after the associated data effects are visible in DUT memory. An interrupt,
    when enabled, follows that publication.
\end{description}

Section~\ref{sec:design} explains the authority and release conditions at each
point. A request identifier correlates an acknowledgment with an access; it
does not establish memory visibility. The method assumes a driver that obeys
the exposed protocol, valid DMA mappings, compatible physical execution, and
a memory path that preserves the required publication order. The order is per
endpoint, not a global total order across devices. These conditions delimit
the method; their statement is not a proof of full protocol equivalence.
