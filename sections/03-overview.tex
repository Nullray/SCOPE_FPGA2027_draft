\section{System Overview}
\label{sec:overview}

\subsection{Software-Defined Device Contract}

Software-defined peripheral access is the \emph{goal}: host software selects a
supported logical PCIe composition and binds its endpoints to compatible
physical devices before DUT enumeration. The native driver consumes the
resulting device contract without needing to know the physical attachment.
Selection is bounded by provisioned FPGA capacity and end-to-end semantic
support. The method considers pre-enumeration configuration, without claiming
arbitrary device protocols or online hotplug.

Two decouplings provide the architectural \emph{means} of achieving this goal,
with different roles.
\emph{Logical presentation--physical device decoupling} separates the contract
discovered by the DUT from the identity and placement of the assigned physical
device, making composition and device assignment software choices.
\emph{Control-semantics--data-path decoupling} separates operations that need
semantic mediation from payload movement. Once control is mediated, this second
separation permits a host-local DMA path without software byte copying. It does
not itself make the device view configurable, which is the role of the first
decoupling. Table~\ref{tab:decoupling} summarizes their distinct consequences.

With these separations, virtualization supplies the selected logical view and
a compatible physical device supplies independently implemented I/O execution
for end-to-end hardware--software interaction.
Mediation changes when operations reach the controller, however, so retained
physical execution does not reproduce direct-attachment timing.
Section~\ref{sec:discussion} examines the tradeoff between configurability and
fidelity.
The prototype evidence in Section~\ref{sec:evaluation} supports pre-silicon
native-driver operation in separate endpoint configurations within that boundary.

\subsection{System Architecture}
\label{sec:architecture}

Figure~\ref{fig:architecture} maps the functional roles of
Figure~\ref{fig:planes} onto the FPGA prototype, local host, and remote host.
The \emph{FPGA front-end}
provides the generic hardware interface consumed by the DUT. A \emph{software
back-end} mediates device behavior on a host; it is distinct from the
\emph{physical device}, which executes compatible work. The \emph{local
software back-end} defines the DUT-visible hierarchy and remains authoritative
for logical device state. When a device is assigned to another host, a
\emph{remote software back-end} mediates physical execution there without
defining a second DUT-visible hierarchy.

Within the local back-end, \emph{device assignment} specifies the supported
logical hierarchy and associates each endpoint with a compatible physical
device and its host location. This unifies what the DUT discovers with where
its work executes, without requiring the two to share a physical attachment.
Runtime control uses four shared
responsibilities: \emph{device state}, \emph{semantic mediation},
\emph{address translation}, and \emph{cross-domain transport}. Corresponding
modules have the same names and positions on both hosts because their roles
persist when attachment changes. Their state authority differs: the local
back-end maintains the logical state consumed by the driver, while the remote
back-end maintains the execution state needed by its assigned device.
These are functional responsibilities, not claims of identical software
objects or replicated controller engines.

Semantic mediation consults device state, interprets operations within the
exposed contract, and invokes address translation before releasing work.
The local back-end prepares a request from the native driver's operation; the
remote back-end, when used, adapts that request to its physical execution
domain. Cross-domain transport carries requests and results across the
DUT--host or host--host boundary. Here, a domain denotes a distinct device-access
or execution environment, not a clock domain. The local transport uses device
assignment to select the local or remote path. A remote request enters the
remote transport through the RDMA interface and proceeds to semantic mediation,
which consults device state and address translation before accessing the
physical device. Results return through mediation and transport. Transport
therefore supplies connectivity; mediation determines when submission or
completion may be released.

The front-end exposes a \emph{device access window} through which the DUT
performs configuration and runtime accesses. Defined configuration reads can
be served from a committed local copy of software state.
\emph{Access event identification} resolves control accesses to their logical
endpoint and operation address, without interpreting device semantics or
choosing the physical host. Cross-domain transport delivers the resulting
events to software and returns responses or committed updates to the access
window. Software-provided interrupt state follows a separate path through
\emph{interrupt delivery} to the DUT. Thus, configuration reads need not make
a software round trip, and responses do not pass back through event
identification. The links in Figure~\ref{fig:architecture} express dependencies
and interfaces rather than a mandatory processing pipeline.

Payload movement remains separate from the control responsibilities. For a
host-local device, an FPGA-exposed DMA aperture makes DUT memory reachable in
the device's address domain, enabling P2P transfer without a software payload
relay. Figure~\ref{fig:architecture} shows that endpoint-to-memory relation
directly, abstracting the mapping and physical routing rather than removing
them. A remote device instead operates in its host's address domain, with
RDMA carrying data between hosts. The depicted remote realization uses
host-mediated payload transfer. Control/data separation therefore permits
different data paths; it does not imply that every path avoids software copying.

RDMA is an instance of location extension, not a separate native-driver
abstraction. The DUT continues to consume the selected device contract, while
the local back-end routes work and the remote back-end preserves compatible
physical execution. Before returning a result, the remote side completes the
required data transfers. The local side then makes the associated data
DUT-visible before publishing logical completion. The obligations remain the
same as for local attachment even though the address domains, copy count, and
latency differ. Section~\ref{sec:design} states the corresponding release
conditions; remote attachment does not imply transparent bus extension or
direct-attachment timing.

Figure~\ref{fig:overview} presents the corresponding two-stage use of this
architecture. Before enumeration, the back-end supplies logical state and
device assignments for the front-end to present the selected hierarchy. During I/O, the
front-end delivers control events to the endpoint context and semantic adapter,
which prepare compatible operations for the physical device. Payload DMA
follows the separate host-local memory path. The repeated component names and
colors connect these operations to the roles in Figure~\ref{fig:architecture}.

Within the control tier introduced in Figure~\ref{fig:planes}, virtualization
combines with compatible passthrough. \emph{Control virtualization} constructs the logical
view and mediates state that differs from the physical device.
\emph{Control passthrough} retains compatible physical execution after any
required address or protocol adaptation. An endpoint can use both, with
passthrough limited to the compatible operations rather than every register or
a full PCIe function assignment. This control choice is independent of the
payload path, which may bypass software byte copying even when submission is
mediated.

\subsection{Distributed Device State and Commit Points}
\label{sec:coherence}

The separation of responsibilities distributes device state across the
front-end, software back-ends, and physical device. To retain the native contract, these
components must preserve publication before ownership transfer and data
visibility before completion. Logical state, translated metadata, and payload
follow different paths, so an access must not become visible merely because one
component has finished processing it. \sys defines three per-endpoint commit
points at which the relevant dependencies have been satisfied:

\begin{description}[leftmargin=*,style=nextline]
    \item[Configuration--route coherence.] A configuration write retires only
    after the authoritative image, its FPGA-visible copy, and any affected
    BAR route agree.
    \item[Submission--DMA coherence.] A physical doorbell transfers ownership
    only after published work has been observed and its translated state is
    visible in the physical device's address domain.
    \item[Data--completion coherence.] Completion becomes driver-visible only
    after the associated data effects are visible in DUT memory. An interrupt,
    when enabled, follows that publication.
\end{description}

These commit points specify release conditions, but request matching alone
cannot establish them. An identifier correlates an acknowledgment with an
access, while memory visibility requires guarantees from the memory path. The
method therefore assumes a driver that obeys the exposed protocol, valid DMA
mappings, compatible physical execution, and preservation of the required
publication order. That order is per endpoint, not a global total order across
devices. Section~\ref{sec:design} details the authority and release conditions
under these assumptions, without claiming a proof of full protocol equivalence.
