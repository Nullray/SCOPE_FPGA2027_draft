\section{System Architecture}
\label{sec:architecture}
\label{sec:overview}
\label{sec:design}

Figure~\ref{fig:architecture} shows how the FPGA front-end and host software
back-ends connect the DUT to local and remote physical devices.

\subsection{Device View and Physical Bindings}

\sys separates the device view presented to the DUT from the physical
devices that execute operations. The device view comprises a logical
device hierarchy and the behavior exposed to DUT drivers. Physical-device
bindings associate logical endpoints with compatible devices on local or
remote hosts. The same logical interface can therefore be retained when
a compatible physical device is substituted or relocated.

Each logical endpoint has a supported driver-visible contract and an
\emph{endpoint context} in host software that tracks its state and
physical-device binding. Host software mediates control operations, while
payloads use a separate DMA or staged-transfer path. Configuration is
limited by FPGA interface capacity, implemented protocol support, and
valid DMA mappings. An endpoint's advertised identity and capabilities
must match the behavior that the back-end and assigned device jointly support.

The prototype exposes logical endpoints through a provisioned PCIe switch
hierarchy. Host software selects active endpoints, their order, supported
device types, and physical-device bindings. The back-end assigns logical
bus/device/function (BDF) identifiers and constructs Type-1 bridge and Type-0
endpoint configuration images containing identity, class, BAR layout, and
supported capabilities. The front-end exposes the committed image through
the enhanced configuration access mechanism (ECAM). Absent functions return
all ones, allowing Linux to enumerate the selected device hierarchy through
its standard PCI subsystem, independently of physical-device placement.
Advertised capabilities match the implementation; for example, the Ethernet
endpoint exposes legacy INTx but does not advertise MSI/MSI-X.

Figure~\ref{fig:overview} shows the configuration lifecycle. Configuration
tools select the device hierarchy and physical-device bindings, which the
local device state manager records. The state manager and FPGA front-end
install the initial configuration image and BAR routes before enumeration.
The DUT OS then discovers functions, assigns resources, and binds drivers.
Configuration writes during this process update the committed image and
affected routes using the mechanism in Section~\ref{sec:configuration-commit}.
Bound drivers initialize their endpoints for I/O. The device hierarchy
remains fixed for the boot. Supported endpoints can be reconfigured before
boot without changing their DUT software or the FPGA bitstream; online
hotplug is outside the current lifecycle.

\subsection{System Components and Data Paths}
\label{sec:components}

The \emph{FPGA front-end} provides the generic
DUT-facing interface. Its \emph{device access window} serves supported
configuration reads from a committed state copy. An \emph{access decoder}
resolves BAR accesses to logical endpoints, and the \emph{transport
interface} forwards control events to host software. Host responses and
configuration updates return to the device access window. A separate
\emph{interrupt controller} delivers software-provided interrupt state to the DUT.

Each \emph{host software back-end} contains a \emph{device state manager},
\emph{semantic adapter}, \emph{address translator}, and \emph{transport
interface}. The local state manager maintains the logical configuration and
endpoint state exposed to DUT drivers. The semantic adapter interprets
device commands and uses address translation to prepare operations for
the assigned physical device. For a remote binding, the local back-end
forwards requests to the remote back-end, whose adapter prepares operations
in that host's address domain. The local back-end remains responsible for
DUT-visible state, while the remote state manager tracks physical execution
at the assigned host.

Host control is implemented in a QEMU-based manager~\cite{bellard2005qemu}
with device-specific adapters. Shared services handle configuration, routing,
event transport, response delivery, and interrupt aggregation. The adapters
maintain queue, address, and outstanding-operation state behind a common
control interface. This structure keeps device-specific protocol logic in
host software and permits reuse of the FPGA front-end. The front-end handles
one outstanding BAR transaction at a time on its shared response channel.
Completion of that control transaction does not imply completion of the
corresponding device operation, which can continue after the BAR response.

The back-end supports two forms of control mediation. \emph{Control
virtualization} maintains the logical state exposed to the driver.
\emph{Control passthrough} invokes compatible physical-device operations
after any required address or protocol adaptation. An endpoint may combine
both forms. Passthrough applies to selected operations and does not imply
assignment of an entire PCIe function. The control choice is independent
of the payload path.

For a local-host device, the FPGA DMA aperture makes DUT memory reachable in
the device's address domain, allowing peer-to-peer (P2P) payload transfer
without software copying. \sys also supports devices on remote hosts.
RDMA connects the software back-ends, which coordinate physical DMA and
payload transfers across address domains. The remote device operates in
its host's address domain, while the local back-end maintains the state
exposed to the DUT. Both paths must satisfy the visibility conditions in
Section~\ref{sec:coherence}.

For example, in the host-staged NVMe path, the local back-end copies write data
from DUT memory to a staging buffer, and RDMA transfers it to buffers
addressable by the remote device before physical submission. Reads follow
the reverse path: physical DMA targets remote buffers, RDMA returns the
payload, and the local back-end publishes it in DUT memory before logical
completion. The remote back-end owns the physical queues, while the local
back-end maintains the driver-visible queues.
Host copies and RDMA transfers add cost while the DUT retains the same
NVMe interface.

Adding an instance of a supported device requires additional configuration,
routing, and endpoint state. Supporting a new protocol also requires a
semantic adapter and a compatible DUT software stack. The generic FPGA
interface can be reused, but presenting more endpoints still consumes
hardware capacity. Section~\ref{sec:evaluation} compares two complete FPGA
configurations; Section~\ref{sec:discussion} explains why that comparison
does not quantify resource growth per endpoint.
