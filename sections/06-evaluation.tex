\section{Evaluation}
\label{sec:evaluation}

We evaluate \sys in terms of peripheral configurability, performance
implications, and controllability of device interactions. We measure
control-path latency and data-path performance across on-board, host-local,
and host-remote configurations, and assess functional support across peripheral
types and backend locations. Finally, we use software-mediated fault injection
to evaluate the error-handling behavior of unmodified DUT drivers.

\subsection{Experimental Setup}

We evaluate \sys on the NEXST FPGA prototyping platform using a XiangShan
RISC-V processor running at 50\,MHz. Table~\ref{tab:platform} summarizes the
hardware and software configuration. The on-board configuration connects the
peripheral directly to the FPGA platform; host-local and host-remote place it
on the FPGA-connected host and a separate RDMA-accessible host, respectively.
The on-board baseline uses a bitstream and device tree configured for direct
PCIe access, whereas both host-based configurations access the peripherals
through \sys. Measurement procedures and workload parameters are described
in the respective subsections.

\noindent\textbf{FPGA resource cost.}
SCOPE replaces the FPGA-resident PCIe Root Port with a lightweight front end.
Post-route reports show that the complete SCOPE configuration uses 8,068 fewer
LUTs (0.85\%), 14,749 fewer flip-flops (2.90\%), and 142 fewer 36-Kb BRAM tiles
(11.72\%) than the original Root Port configuration. Percentages are relative
to the total resource usage of the original configuration.

\subsection{Control-Path Overhead}

We characterize the cost of software-mediated NVMe access using a BAR-write
microbenchmark and an SQ doorbell write during command submission. For both
measurements, timestamps are taken on the DUT before the register write and
after the subsequent I/O fence. Elapsed cycles are measured using the RISC-V
cycle counter and converted to time using the DUT's 50\,MHz clock. The BAR
probe targets the read-only NVMe Version (VS) register at offset \texttt{0x08}.
The doorbell measurement is performed during the submission of a real 4-KiB
NVMe read; the subsequent wait for command completion is excluded from the
timed interval.

Table~\ref{tab:control} shows that BAR write latency increases from
2.448\,\si{\micro\second} for on-board access to 16.624\,\si{\micro\second}
for host-local access and 468.370\,\si{\micro\second} for host-remote access.
SQ doorbell submission takes 4.692\,\si{\micro\second},
59.379\,\si{\micro\second}, and 1113.010\,\si{\micro\second} for the three
configurations, respectively. The host-based paths introduce FPGA event
forwarding and software processing, with remote access additionally traversing
the RDMA connection. SQ doorbell submission also requires queue handling and
backend processing.

These control-path costs are the price of enabling flexible access to
host-local and remote peripherals. For the functional and driver-validation
tasks targeted by \sys, the key question is whether this flexibility preserves
device functionality and native driver behavior while enabling controlled
fault injection and observation of driver responses. The functional and
fault-injection experiments evaluate this capability, while the next subsection
examines sustained I/O performance across the three configurations.

\subsection{NVMe Data Path}

Table~\ref{tab:nvme} compares the on-board/P2P path with the host-attached path
under the recorded DUT read workloads. Sequential-read bandwidth retains
99.1\% of the host-attached result, and random-read throughput retains 98.5\%.
This contrast with the control-path latency supports the architectural choice
to keep payload movement off the software event channel.

The recorded tests cover reads at queue depth one. They do not establish write
performance, queue-depth scaling, or equivalence across local and remote
backends. Those dimensions require a controlled sweep with the same device,
requester, workload, repetition count, and timing boundary.

\subsection{NIC Data Path}

The single-queue 82580 backend sustains 56.65 and
46.82\,\si{\mega\bit\per\second} for TCP in the DUT-to-peer and peer-to-DUT
directions, respectively. UDP reaches 4.90 and
7.75\,\si{\mega\bit\per\second}, and ping RTT is
2.80\,\si{\milli\second}. These results establish bidirectional descriptor
translation, payload transfer, completion, and interrupt handling. Without a
matched direct/on-board NIC baseline and the missing workload parameters, they
do not support a line-rate or relative-performance claim.

\subsection{Configuration and Native-Driver Compatibility}

The functional experiment holds the FPGA bitstream and DUT software constant
and changes the enabled endpoint and backend binding in the host configuration.
Linux enumerates the resulting hierarchy and binds its standard \texttt{nvme}
or \texttt{igb} driver. The NVMe path completes queue setup and storage reads;
the NIC path completes link setup, address configuration, ping, and bidirectional
packet transfer. These tests exercise configuration, runtime control, translated
DMA, completion, and interrupt delivery. They demonstrate two device types in
separate configurations. Simultaneous NVMe and NIC operation has not been
measured and is not inferred from the independent runs.

\subsection{Completion and Interrupt Ordering}

Across 100 trigger-and-clear trials, the DUT observed the expected interrupt
transition without timeout or an unexpected event. After subtracting the
measurement baseline, interrupt injection latency is
956.81\,\si{\nano\second}. Together with successful NVMe and NIC transfers,
this result checks the externally visible consequence of the ordering rules:
the driver sees returned data and completion state before it is notified. The
experiment does not independently expose every internal happens-before edge;
Figure~\ref{fig:coherence} states the design contract that the implementation
must maintain.

\subsection{Limits of the Current Evaluation}

The functional and performance results establish single-endpoint operation for
the tested NVMe and NIC configurations. They do not quantify simultaneous
multi-device interference or the resource slope of increasing the provisioned
endpoint capacity. Consequently, the paper claims a parameterized generic
mechanism, not measured 13-device scalability. Repeated workload runs with
dispersion, a matched NIC baseline, and synthesis at multiple capacities are
needed before making stronger throughput, tail-latency, or FPGA-scaling claims.
