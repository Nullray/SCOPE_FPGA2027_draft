\section{Evaluation}
\label{sec:evaluation}

The evaluation asks whether supported device views can change without changing
the FPGA interface or DUT software, whether native drivers can use the mediated
contract, and what control-path cost the prototype incurs. It then separates
observed results from measurements still needed to assess payload performance,
concurrent composition, and FPGA capacity scaling. Functional compatibility
does not imply direct-attachment timing fidelity.

Several numerical records below also appear in
\sysprevious~\cite{scope2026fpt}: the proxy BAR-write round trips, direct MMIO
references, NVMe P2P reads, and virtual interrupt injection. They characterize
the preceding routing substrate and are retained as context, not independent
measurements of \sys's configurable device presentation. The native-driver
functional tests and the planned matched comparisons address that additional
boundary. Raw-log reconciliation is still required before attributing costs
to individual mechanisms.

\subsection{Experimental Setup}

The prototype connects a XiangShan RISC-V FPGA system to an x86 host. A
QEMU-based host software back-end selects the logical device view and assigns
compatible physical devices before DUT enumeration. The same FPGA interface
is used in the two evaluated single-endpoint configurations. The tested NIC
configuration uses one queue pair and legacy INTx; Table~\ref{tab:platform}
records the platform and scope needed to interpret the measurements.

The proxy result times a BAR access observed by the DUT through the FPGA and
host software back-end. Direct Control times an MMIO write without semantic
mediation. A separate NVMe result includes submission processing and address
translation before physical execution. These are distinct operations and
cannot be treated as an overhead decomposition. The Direct Control tests also
use ARM A53 and RocketChip requesters rather than the XiangShan proxy setup;
they provide context, not matched baselines. Raw run identifiers, commands,
repetition counts, and dispersion remain to be supplied, so the numerical
entries below are retained as draft measurements.

\subsection{Configuration and Native-Driver Compatibility}

The functional experiment holds the FPGA bitstream and DUT software constant
and changes the supported logical endpoint and its physical-device assignment
in host configuration.
Linux enumerates the resulting hierarchy and binds its standard \texttt{nvme}
or \texttt{igb} driver. The NVMe path completes queue setup and storage reads;
the NIC path completes link setup, address configuration, ping, and bidirectional
packet transfer. These tests exercise configuration, runtime control, translated
DMA, completion, and interrupt delivery. They demonstrate two device types in
separate configurations. Simultaneous NVMe and NIC operation has not been
measured and is not inferred from the independent runs.

\subsection{Control-Path Cost}

Table~\ref{tab:control} separates measurements by requester and timing boundary.
Proxy Forwarding records tens of microseconds on a path that crosses the FPGA
event channel and host software back-end. The NVMe semantic-submission value exceeds
the BAR-write value and includes queue inspection and address translation.
Without component timestamps or an ablation, these aggregates do not isolate
the cost of those operations. Direct Control
provides a nanosecond-scale reference for an MMIO path that does not perform
those semantic operations; it is not an ablation in which an arbitrary mediated
submission can be safely bypassed.

Figure~\ref{fig:measurement-boundaries} makes the three timed intervals
explicit. The direct-control path uses different requesters and omits the
semantic proxy, so its value cannot be subtracted from a proxy measurement to
isolate mediation cost.

\subsection{NVMe Data Path}

Table~\ref{tab:nvme} retains the draft's host-attached and on-board/P2P
measurements pending provenance reconciliation. Their arithmetic ratios are
99.1\% and 98.5\%, respectively. The available manuscript and slide records
disagree on the underlying throughput and IOPS values; the requester, path,
queue depth, and units must be matched to raw logs before interpreting these
ratios as end-to-end \sys performance. They are excluded from the abstract's
performance claims.

The draft labels these reads as queue depth one. At 240372.3 IOPS, one
outstanding request would imply approximately 4.16\,\si{\micro\second} per I/O.
This cannot describe the same serial per-I/O path as a
61.41\,\si{\micro\second} submission unless the timing scope or submission
policy differs. It is a provenance check, not evidence that either value is
incorrect. A matched experiment must resolve the difference and report the
device, requester, workload, repetition count, and timing boundary.

\subsection{NIC Data Path}

The assigned single-queue 82580 physical NIC sustains 56.65 and
46.82\,\si{\mega\bit\per\second} for TCP in the DUT-to-peer and peer-to-DUT
directions, respectively. UDP reaches 4.90 and
7.75\,\si{\mega\bit\per\second}, and ping RTT is
2.80\,\si{\milli\second}. These observations support functional bidirectional
I/O for the tested configuration; they do not independently verify every
descriptor transition or ordering condition. A matched NIC baseline and complete
workload parameters are still needed to assess relative performance. These
records do not support a line-rate claim.

\subsection{Interrupt Delivery and Ordering Evidence}

\sysprevious reports 100 interrupt injection and clearing trials without
timeouts or unexpected events~\cite{scope2026fpt}. After subtracting the
measurement baseline, interrupt injection latency is
956.81\,\si{\nano\second}. These inherited trials support interrupt delivery and clearing
under the tested conditions, not data-before-completion ordering. Successful I/O
alone cannot rule out ordering violations that depend on timing or concurrency.
Figure~\ref{fig:coherence} specifies the required contract rather than a measured
ordering result. Validation needs instrumented traces or litmus tests that
check payload visibility before both polled completion and interrupt handling,
including concurrent traffic, mask changes, and reset. The baseline subtraction
method and variability of the latency estimate also remain to be documented.

\subsection{Limits of the Current Evaluation}

The functional and performance results establish single-endpoint operation for
the tested NVMe and NIC configurations. They do not quantify simultaneous
multi-device interference or the resource slope of increasing the provisioned
endpoint capacity. Consequently, the paper claims a parameterized generic
mechanism, not measured 13-device scalability. Repeated workload runs with
dispersion, a matched NIC baseline, and synthesis at multiple capacities are
needed before making stronger throughput, tail-latency, or FPGA-scaling claims.
