\section{Evaluation}
\label{sec:evaluation}

We evaluate \sys in terms of peripheral configurability, performance
implications, and controllability of device interactions. We measure
control-path latency and data-path performance across on-board, host-local,
and host-remote configurations, and assess functional support across peripheral
types and backend locations. Finally, we use software-mediated fault injection
to evaluate the error-handling behavior of unmodified DUT drivers.

\subsection{Experimental Setup}

We evaluate \sys on the NEXST FPGA prototyping platform using a XiangShan
RISC-V processor running at 50\,MHz. Table~\ref{tab:platform} summarizes the
hardware and software configuration. The on-board configuration connects the
peripheral directly to the FPGA platform; host-local and host-remote place it
on the FPGA-connected host and a separate RDMA-accessible host, respectively.
We use iWARP to match the RDMA capabilities of our existing Ethernet adapters.
The same remote-peripheral approach could be adapted to other RDMA transports,
although this evaluation uses only iWARP.
The on-board baseline uses a bitstream and device tree configured for direct
PCIe access, whereas both host-based configurations access the peripherals
through \sys. Measurement procedures and workload parameters are described
in the respective subsections.

\noindent\textbf{FPGA resource cost.}
SCOPE replaces the FPGA-resident PCIe Root Port with a lightweight front end.
Post-route reports show that the complete SCOPE configuration uses 8,068 fewer
LUTs (0.85\%), 14,749 fewer flip-flops (2.90\%), and 142 fewer 36-Kb BRAM tiles
(11.72\%) than the original Root Port configuration. Percentages are relative
to the total resource usage of the original configuration.



\subsection{Control-Path Overhead}

We characterize the cost of software-mediated NVMe access using a BAR-write
microbenchmark and an SQ doorbell write during command submission. For both
measurements, timestamps are taken on the DUT before the register write and
after the subsequent I/O fence. Elapsed cycles are measured using the RISC-V
cycle counter and converted to time using the DUT's 50\,MHz clock. The BAR
probe targets the read-only NVMe Version (VS) register at offset \texttt{0x08}.
The doorbell measurement is performed during the submission of a real 4-KiB
NVMe read; the subsequent wait for command completion is excluded from the
timed interval.

Table~\ref{tab:control} shows that BAR write latency increases from
2.448\,\si{\micro\second} for on-board access to 16.624\,\si{\micro\second}
for host-local access and 468.370\,\si{\micro\second} for host-remote access.
SQ doorbell submission takes 4.692\,\si{\micro\second},
59.379\,\si{\micro\second}, and 1113.010\,\si{\micro\second} for the three
configurations, respectively. The host-based paths introduce FPGA event
forwarding and software processing, with remote access additionally traversing
the RDMA connection. SQ doorbell submission also requires queue handling and
backend processing.

These control-path costs are the price of enabling flexible access to
host-local and remote peripherals. For the functional and driver-validation
tasks targeted by \sys, the key question is whether this flexibility preserves
device functionality and native driver behavior while enabling controlled
fault injection and observation of driver responses. The functional and
fault-injection experiments evaluate this capability, while the next subsection
examines sustained I/O performance across the three configurations.



\subsection{Data-Path Performance}
\label{sec:data-path-performance}

The control-path measurements show that software mediation increases the
latency of individual control operations. We next examine whether this
increase is accompanied by a comparable loss in sustained I/O throughput.
We evaluate NVMe across on-board, host-local, and host-remote configurations
using fio with direct I/O, a single job, and a queue depth of one. For each
workload, we use the same workload parameters across the three configurations
and report the mean over three 60-second runs.

Table~\ref{tab:nvme} shows that host-local access preserves near-baseline read
performance despite its software-mediated control path. For both 128-KiB
sequential reads and 4-KiB random reads, performance differs from the on-board
baseline by less than 2\%. Sequential and random write performance is lower
by 4.4\% and 13.1\%, respectively. Host-remote access offers a different
tradeoff: it enables the DUT to access a physical NVMe device on another host
through its native NVMe driver. Its 128-KiB sequential read and write
throughput reaches 49.1\% and 38.8\% of the on-board baseline, respectively.

Figure~\ref{fig:nvme-throughput} extends this comparison across fio transfer sizes from 4 KiB to
1 MiB. Host-local read throughput tracks the on-board baseline throughout
the sweep, remaining within 4.1\%, while the write-throughput gap reaches
18.4\% at 1 MiB. Host-remote throughput also increases with transfer size,
reaching 11.81 MiB/s for reads and 8.20 MiB/s for writes at 1 MiB.

These results show that software-mediated control need not impose a
proportional penalty on sustained I/O performance: host-local reads remain
close to the on-board baseline even though individual control operations
are slower. Remote placement trades throughput for backend-location
flexibility, allowing the DUT to access a physical NVMe device across hosts
through its native software stack.

\subsection{Functional Validation}
\label{sec:functional-validation}

We evaluate the extensibility of \sys using representative peripherals spanning
conventional I/O devices and compute accelerators. The experimental platform
combines a XiangShan FPGA prototype, x86 hosts, and U280 accelerator boards.
In a heterogeneous configuration, \sys concurrently exposes NVMe storage,
Ethernet networking, a Vortex GPGPU, and an FSA attention accelerator to the
DUT. Table~\ref{tab:peripheral-validation} summarizes these representative
devices, their software stacks, and the functional workloads used for validation.



Beyond enumeration and driver binding, we validate accelerator execution
using workloads launched from the XiangShan prototype. All Vortex workloads
listed in Table~\ref{tab:peripheral-validation} pass their application-level
correctness checks. Figure~\ref{fig:vortex-functional-trace} presents a
representative convolution-test trace from the XiangShan DUT, showing input
and weight uploads, kernel loading, accelerator execution, output retrieval,
and a successful result check. These tests validate the integrated operation
of the DUT-side software stack and the physical accelerator.



Taken together, these cases demonstrate that \sys can provide an FPGA
processor prototype with a configurable environment of heterogeneous
peripherals at different backend locations. Device-specific mediation in host
software supports the integration of peripherals with different control
interfaces and execution models. This enables the processor prototype to
exercise drivers, runtimes, and application workloads with physical devices
before processor silicon is available, broadening pre-silicon validation from
peripheral discovery and driver binding to end-to-end processor--peripheral
functionality.

\subsection{Fault Injection}
\label{sec:fault-injection}

\begin{sloppypar}
Beyond peripheral connectivity, \sys provides software-controlled fault
injection by selectively intervening in interactions between the DUT and
physical peripherals. Error conditions that depend on particular device states,
event sequences, or timing can be difficult to trigger on demand with physical
devices alone. This control allows developers to introduce targeted abnormal
conditions while retaining the physical backend and the unmodified DUT driver.
We demonstrate the capability with three NVMe cases targeting controller
initialization, command submission, and completion notification.
Table~\ref{tab:fault-injection} links each intervention to the observed
native-driver behavior and subsequent recovery checks.
\end{sloppypar}



The cases exercise distinct error-handling paths. Initialization aborts when
the ready state is withheld despite the physical controller being ready.
Dropping the target SQ doorbell triggers timeout handling followed by
controller reset. In contrast, suppressing only the completion notification
leaves the successful CQE available for the driver to discover by polling on
timeout, with no controller reset observed.

These cases demonstrate how software mediation extends FPGA-based pre-silicon
validation beyond normal peripheral operation. By controlling interactions
with a physical backend, \sys allows the DUT's native driver to encounter
selected fault conditions and exercise error-handling paths that successful
I/O alone does not test. This makes abnormal device interactions an explicit,
software-controlled part of prototype validation, without requiring changes
to DUT software or waiting for naturally occurring hardware faults.
