\subsection{State Ownership and Commit Points}
\label{sec:coherence}

The host back-end maintains each endpoint's logical state, the FPGA holds
a committed configuration copy, and the assigned physical device executes
I/O operations. Figure~\ref{fig:coherence} summarizes three per-endpoint
commit points that coordinate these components. Configuration retirement
(C1) allows the DUT to complete a configuration write after the updated
configuration and routes are installed in the FPGA. Physical submission
(C2) releases work after its metadata and required input data are visible
to the device. Logical
completion publication (C3) makes completion visible to the DUT driver
after the corresponding data is visible in DUT memory.

Here, \emph{coherence} denotes consistency between related device states and
the order in which components observe them. It does not denote a
cache-coherence protocol. Request identifiers associate events with
operations, but memory visibility requires ordering in the underlying
memory path. The commit conditions assume protocol-compliant drivers,
valid DMA mappings, compatible devices, and a memory path that preserves
the required publication order. They apply to dependent operations within
each endpoint. Independent requests may complete in the order allowed by
their device protocols, with no global order imposed across devices.

\subsubsection{Configuration--Route Coherence}
\label{sec:configuration-commit}

The local back-end maintains the authoritative writable configuration state.
The initial configuration image and route state are installed before
enumeration. During enumeration and subsequent operation, the front-end holds
each supported configuration write pending and reports it as a control event.
The back-end applies the configuration-field semantics and updates the
FPGA's committed copy and any affected BAR route. To prevent use of a
partially updated route, it invalidates the entry before replacing its
address fields and writes the validity field last. A readback fence orders
these updates before the matching acknowledgment, which permits the DUT
to complete the configuration write at C1.

The acknowledgment identifies the pending write, while the ordered updates
make the new configuration and route visible in the FPGA. The DUT cannot
complete the write before its associated route update is installed.
Configuration reads use the committed front-end copy, with the local
back-end retaining authority over writable state.

\subsubsection{Submission--DMA Coherence}
\label{sec:submission-commit}

The native driver publishes queue entries in DUT memory before signaling
submission. The adapter reads the published queue range through its memory
mapping, checks entry stability, translates address-bearing metadata and
indirect references, and records pending work in the endpoint context.
At C2, the adapter may submit the operation to the physical device only
after translated metadata and any required input data are visible in
that device's address domain. A BAR response can acknowledge the DUT's
control access before C2; it does not indicate that the physical request
has been submitted or completed.

The local-host NVMe adapter illustrates this preparation. A submission queue
entry (SQE) contains physical region page (PRP) references in the DUT address
domain. The adapter derives transfer length from command and namespace state,
translates PRP1/PRP2, and follows PRP lists to translate data-page and
next-list references. It writes the adapted metadata through the shared
mapping and verifies writeback before issuing the physical SQ doorbell.
The translated references resolve through the FPGA DMA aperture, allowing
the controller to transfer payload while software handles command metadata.
Translating the queue base alone would leave nested payload references
in the wrong address domain.

Checking a stable queue entry does not ensure that preceding driver writes
have reached the adapter.
The memory path must make driver writes visible to the adapter before
inspection and translated metadata visible to the physical device before
submission. A transport
without these properties needs ordered staging or an explicit visibility
mechanism. An acknowledgment that identifies a request cannot replace
this ordering. A remote adapter must meet the same C2 requirements in the
remote device's address domain.

Figure~\ref{fig:semantic-dma} separates metadata preparation from local-host
payload DMA. The adapter translates buffer references before C2, and the
physical device then uses those references for payload DMA. The aperture
provides address reachability, while the memory path must preserve data
visibility.

Ethernet and accelerator adapters apply the same submission requirements
to their device protocols.
The Ethernet back-end translates ring and descriptor buffer addresses while
preserving reset and interrupt cause/mask semantics. The back-end for the
Vortex GPGPU~\cite{tine2021vortex}
handles DUT commands, translates memory operands, and maintains separate
logical and physical queue state. Adapted DUT software accesses the Vortex
endpoint through its device-specific transport, with completion and error
states returned through the logical queue. Both adapters specialize protocol
handling and address interpretation while reusing presentation, dispatch,
and transport.

\subsubsection{Data--Completion Coherence}
\label{sec:completion-commit}

The adapter validates physical completion or writeback and matches it to
outstanding work recorded in the endpoint context. For a remote binding,
the remote back-end completes required data transfers before returning the
result. C3 marks the point at which logical completion becomes visible to
the DUT driver, after the corresponding data effects are visible in DUT
memory. This requirement applies both to completion written by software
and to a record made valid by direct DMA. Physical completion may occur
earlier, while the data is still being transferred or made visible to the DUT.

For software-published completion, the local back-end finishes required
data and writeback publication before releasing the completion. For a
directly DMA-visible record, the physical device and memory path must make
the data visible before the record's valid or ownership indication.
Back-end polling or a delayed interrupt cannot prevent a driver from
observing a record that has already become valid too early.

For local-host NVMe, the adapter validates a completion queue entry (CQE)
by checking its phase, queue identifier, and command identifier against
outstanding work. The controller writes CQEs directly to DUT memory through
the aperture, so the host adapter checks completions for request tracking
and notification. The DUT driver can observe CQEs independently of that
check. A valid CQE indicates data visibility only if data-before-completion
ordering is preserved through the aperture and DUT mapping. Coherent
access alone does not establish this order.

For interrupt-enabled endpoints, the local back-end updates completion-related
pending and interrupt state after C3. The shared level interrupt aggregates
eligible endpoint states, so clearing one endpoint does not clear another.
Polling drivers read the completion record without waiting for this
notification. In both cases, the corresponding data must already be visible
at C3. Per-vector interrupt delivery is outside the demonstrated scope.
