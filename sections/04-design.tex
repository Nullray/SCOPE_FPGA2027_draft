\section{Design}
\label{sec:design}

\sys coordinates a distributed device contract through explicit commit points.
The host software back-end owns logical state, the FPGA front-end exposes its
committed view, and the assigned physical device consumes translated work.
Figure~\ref{fig:coherence} identifies the events that release an access or
transfer ownership. This differs from Figure~\ref{fig:driver-contract}, which
shows why reachability alone cannot provide the native-driver contract.

\subsection{Defining and Committing the Device View}
\label{sec:configuration-commit}

Software selects a logical composition and binds each endpoint to a physical
device before enumeration. A selected contract must be realizable by both the
device-semantic adapter and the assigned controller: every exposed operation
needs a supported path from driver request to physical effect and back.
Changing a binding can preserve that contract when the replacement device is
compatible. Changing identity fields cannot make an incompatible device
execute a different protocol.

their architectural constraints. It describes the method's configuration

The back-end is authoritative for writable configuration state. The front-end
serves reads from a shadow of that state, while access routes determine where
the discovered address ranges lead. Initial enumeration is enabled only after
both the image and routes have been installed. Subsequently, the front-end
holds a configuration write pending and reports it as a control event. The
back-end applies the change, installs the corresponding shadow and any affected
route, and then acknowledges that event. The front-end completes the DUT write
only on the matching acknowledgment.

Write retirement is the commit point for subsequent dependent DUT accesses.
The updates need not occur simultaneously in host and FPGA memory, but their
installation must precede the acknowledgment. Request matching prevents the
wrong write from retiring; the visibility of installed state is a separate
requirement on the control path. This distinction prevents a new BAR assignment
from retiring while an old route is still in use. The shadow accelerates reads
without becoming an independent device model.

\subsection{Admitting Work and Transferring Ownership}
\label{sec:submission-commit}

A runtime control access is dispatched to its endpoint context and
device-semantic adapter. The adapter reconciles operations whose logical state
or address domain differs from what the physical device can consume.
Compatible physical operations retain controller execution. The common
transport identifies the endpoint; the adapter supplies the protocol meaning
of queue setup, submission, completion, and interrupt-visible state.

A submission moves through three semantic states: published by the driver,
prepared for the physical device, and owned by that device. The native driver
publishes work in DUT memory before signaling submission. The adapter observes
the published queue range through the shared memory mapping and checks that
the entry being inspected is stable. It then translates address-bearing
metadata, including indirect references, and records the work in the endpoint's
pending state. Translated metadata must be device-visible before the adapter
issues the physical doorbell. That doorbell, rather than arrival of the
original BAR event, commits the ownership transfer.

This sequence prevents the controller from consuming an untranslated reference,
but its first and last transitions depend on memory ordering. A stable
snapshot can detect an entry changing during inspection; repeated agreement
does not prove that all preceding driver writes have arrived. The host-local
path therefore requires the shared mapping to preserve driver publication
before adapter inspection and translated-state visibility before physical
submission. A transport that cannot provide those properties needs an ordered
staging or visibility mechanism before it can satisfy the same contract.
An event acknowledgment is not a replacement for that memory-path guarantee.

from movement of payload bytes. The adapter changes reachability, while the
physical device can retain the actual transfer.

\subsection{Publishing Completion and Returning Ownership}
\label{sec:completion-commit}

Address retargeting does not require software copying of the payload. For a
host-local device, translated references can reach DUT memory through the
FPGA DMA aperture. A remote device may instead require staging or another
transport-specific path. Reachability and visibility are distinct properties:
any chosen path must preserve the memory ownership and publication conditions
of the exposed contract, even when its copy count and timing differ.

Completion returns ownership to the driver. The adapter associates a
protocol-valid completion or writeback with outstanding work in the owning
endpoint context before advancing logical state. Completion publication is
the first point at which the DUT can observe that work as complete, including
through polling. If software publishes a logical completion, it must do so
after the associated data and writebacks are DUT-visible. Where a completion
record is directly DMA-visible to the DUT, the physical device and memory path
must order data before the record's valid or ownership indication. Back-end
polling or a delayed interrupt cannot repair an already visible early record.

For the host-local path, observing a protocol-valid physical completion can
establish preceding data visibility only if the device's write ordering is
preserved through the DMA aperture and DUT memory mapping. Coherent access
removes a copying requirement, not this ordering dependency. This memory-path
property is an explicit assumption of the method, rather than a consequence
of matching control-event sequence numbers.

After completion publication, the back-end updates the endpoint's pending
and interrupt state. The prototype's shared level interrupt aggregates
eligible pending states, so consuming or clearing work for one endpoint does
not clear another endpoint's state. An interrupt is a notification of published
completion, not the event that makes the payload safe to read. Per-vector
delivery remains outside the demonstrated contract.

\subsection{Capacity and Adaptation Cost}

The FPGA front-end supplies protocol-independent interface capacity.
Supporting another logical instance consumes configuration and routing state;
supporting another device type extends the semantic contract in host software.
The architectural hypothesis is that FPGA cost follows generic capacity rather
than replicated controller engines. The planned 1/2/4/8/13-slot synthesis sweep
in Section~\ref{sec:evaluation} is needed to quantify that hypothesis, while
matched control and data measurements are needed to expose the cost of software
mediation. Neither the contract nor the commit-point diagram substitutes for
those measurements.
