\section{Design}
\label{sec:design}

\sys preserves the distributed device contract by controlling when state
becomes visible and ownership changes. The local software back-end owns logical
state, the FPGA front-end exposes its committed view, and the assigned physical
device consumes translated work, with remote mediation when required by its
location. Their coordination follows the dependencies
motivated in Figure~\ref{fig:driver-contract}.
Figure~\ref{fig:coherence} identifies the corresponding commit points that
release an access or transfer ownership.

\subsection{Defining and Committing the Device Contract}
\label{sec:configuration-commit}

Software selects a logical composition and binds each endpoint to a physical
device before enumeration. A selected contract must be realizable by both the
device-semantic adapter and the assigned controller: every exposed operation
needs a supported path from driver request to physical effect and back. This
condition permits a change of assignment when the replacement device is compatible,
but a change of identity fields cannot make an incompatible device execute a
different protocol.

Table~\ref{tab:configuration-freedom} relates each configurable choice to the
constraint that remains. The table defines the scope of software selection,
without implying that every permitted configuration has been tested.

Once a contract is selected, the local back-end remains authoritative for writable
configuration state. The front-end's device access window serves defined
configuration reads from a committed copy of that state
and uses routes to resolve the discovered address ranges. Because the image and
routes describe the same device view, both must be installed before initial
enumeration is enabled. Later configuration writes can change that view, so
the front-end holds each write pending and reports it as a control event. The
local back-end applies the change and installs the corresponding state copy and any
affected route before acknowledging the event. Only the matching acknowledgment
allows the front-end to complete the DUT write.

Write retirement is therefore the commit point for subsequent dependent DUT
accesses. Host and FPGA updates need not be simultaneous, but the installed
state must be visible before acknowledgment. Request matching ensures that the
right write retires, while this visibility condition ensures that its effects
are usable. Together, these conditions prevent a new BAR assignment from
retiring while an old route remains in use. The front-end copy can thus accelerate
reads while remaining a cache of authoritative state rather than an independent
device model.

\subsection{Admitting Work and Transferring Ownership}
\label{sec:submission-commit}

A committed device contract establishes where runtime accesses are routed.
Access event identification resolves the logical endpoint, and cross-domain
transport dispatches the access to its endpoint context and device-semantic
adapter. Semantic mediation interprets queue setup, submission, completion,
and interrupt-visible state. Where logical state
or the address domain differs from what the physical device can consume, the
adapter reconciles that difference before a compatible operation reaches the
controller.

A submission moves through three semantic states: published by the driver,
prepared for the physical device, and owned by that device. The native driver
publishes work in DUT memory before signaling submission. The adapter observes
the published queue range through the shared memory mapping and checks that the
entry being inspected is stable. It then translates address-bearing metadata,
including indirect references, and records the work in the endpoint's pending
state. Preparation is complete only when the translated metadata is visible to
the physical device. The adapter can then issue the physical doorbell, which
commits the ownership transfer. Arrival of the original BAR event only begins
this process.

For a remote assignment, preparation spans both software back-ends. Local
mediation derives the request from DUT-published work and selects the assigned
host. Remote mediation prepares compatible physical operations, with address
translation resolving references in the remote device's domain. Physical
submission still waits for prepared work and its required data to be visible.
The additional host boundary changes where these conditions are established,
not the ownership-transfer rule.

The sequence protects against consumption of untranslated references only if
its publication and preparation steps preserve memory ordering. Checking
stability can detect changes to an entry during inspection, but agreement
across observations does not prove that all preceding driver writes have
arrived. The host-local
path therefore requires the shared mapping to preserve driver publication
before adapter inspection and translated-state visibility before physical
submission. A transport that cannot provide those properties needs an ordered
staging or visibility mechanism to satisfy the same contract. Correlating an
event acknowledgment with a submission cannot supply that memory-path guarantee.

Preparing control metadata does not require software copying of payload bytes.
For a host-local device, translated references can reach DUT memory through the
FPGA DMA aperture, allowing the physical device to perform the transfer.
Figure~\ref{fig:semantic-dma} separates this payload path from metadata
preparation. In the remote realization, physical DMA is coupled with RDMA
transfer between host address domains. The depicted host-mediated path does
not require the remote device to access DUT addresses directly. Each path
must preserve the memory ownership and
publication conditions of the exposed contract, even when its copy count and
timing differ. Address reachability alone does not establish visibility.

\subsection{Publishing Completion and Returning Ownership}
\label{sec:completion-commit}

Completion closes the submission cycle by returning ownership to the driver
after execution. Before advancing logical state, the adapter associates
a protocol-valid completion or writeback with outstanding work in the owning
endpoint context. Completion publication is the first point at which the DUT
can observe that work as complete, whether by polling or notification. It must
therefore follow visibility of the associated data and writebacks.

On a remote path, the remote back-end associates a valid physical result with
outstanding work and finishes the required data return before transmitting
that result. The local back-end then waits for DUT-visible data before
constructing and publishing logical completion. Physical and logical
completion state may advance independently; their relation is governed by
publication dependencies rather than direct copying of the physical record.

How this order is established depends on the completion path. If software
publishes a logical completion, it must wait until the data and writebacks are
DUT-visible. If a completion record is directly DMA-visible to the DUT, the
physical device and memory path must order data before the record's valid or
ownership indication. Once an early record is visible, back-end polling or a
delayed interrupt cannot repair the violation.

For the host-local path, observing a protocol-valid physical completion can
establish preceding data visibility only if the device's write ordering is
preserved through the DMA aperture and DUT memory mapping. Coherent access can
remove the need for copying, but completion still depends on this ordering
property. The method assumes it explicitly because matching control-event
sequence numbers cannot establish visibility of device writes.

Once completion is published, the local back-end updates the endpoint's pending and
interrupt state. The prototype's shared level interrupt aggregates eligible
pending states, so consuming or clearing work for one endpoint does not clear
another endpoint's state. This notification follows publication and does not
itself make the payload safe to read. Per-vector delivery remains outside the
demonstrated contract.

\subsection{Capacity and Adaptation Cost}

These coordination rules use protocol-independent interface mechanisms in the
FPGA front-end. Another logical instance consumes configuration and routing
state, while another device type extends the semantic contract in host software.
This partition motivates the hypothesis that FPGA cost follows generic capacity
rather than replicated controller engines. The planned 1/2/4/8/13-slot synthesis
sweep in Section~\ref{sec:evaluation} is needed to quantify that growth. Its
resource results must be considered alongside matched control and data
measurements, since shifting semantics into software also introduces mediation
cost. The architectural partition establishes what to measure, not the size of
the benefit.
