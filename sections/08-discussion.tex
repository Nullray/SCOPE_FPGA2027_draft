\section{Discussion and Limitations}
\label{sec:discussion}

\subsection{Configurability and Validation Fidelity}

\sys lets software select a supported logical device hierarchy while
physical devices execute I/O. Validation fidelity depends on protocol
compatibility, the physical behaviors exercised, and mediation's effects
on timing and concurrency. The evaluation demonstrates unmodified Linux
NVMe and Ethernet driver operation and correct results for the tested
accelerator workloads. Coverage is limited to those operations, and the
tests do not establish timing equivalence to direct attachment. Because the
DUT interface is above the PCIe link, link training, link-layer recovery,
and electrical behavior remain outside the validation scope.

Control mediation and direct DMA must obey the ordering conditions in
Section~\ref{sec:coherence}. In particular, a completion record must not
become valid before its associated data is visible to the DUT, including
when the driver polls without interrupts. The implementation therefore
depends on a memory path that preserves data-before-completion ordering.
Successful workloads demonstrate functional operation in the tested cases,
but do not prove that the required ordering holds for every execution.

\subsection{Mediation Cost and Scaling}

On the 50-MHz DUT at an NVMe queue depth of one, local-host reads remain close
to the on-board baseline despite longer control accesses, while the remote
path has lower throughput. The measured control interval runs from a
register write through its subsequent I/O fence. It does not identify
when physical submission at C2 or command completion occurs. Costs at
higher submission rates require additional measurements.

PCIe performance also depends on host implementation and driver
behavior~\cite{neugebauer2018pcie}. The direct baseline uses a different
bitstream and device tree, so the throughput comparison cannot isolate the
effect of software mediation. The resource comparison likewise reports
totals for two complete FPGA configurations; it does not measure incremental
resource use per endpoint. Measurements with deeper queues and concurrent
I/O, host CPU usage, and an endpoint-capacity sweep are needed to quantify
how control overhead and resource use scale.

\subsection{Validity and Generalization}

The LOC counts in Section~\ref{sec:integration-effort} describe the
distribution of code within the local software back-end. They do not
measure development time or total integration effort across remote software,
DUT software, and shared infrastructure. Configuring an already supported endpoint uses
the existing interface. Implementing another protocol still requires
adaptation of submission, memory ownership, completion, and interrupt
behavior.

\sys supports peripherals on remote hosts while the local back-end
maintains the device view exposed to the DUT. The remote back-end
coordinates physical execution in its host's address domain under the
same submission and completion requirements. In the host-staged NVMe
example, payload copies and RDMA transfers add work compared with direct
local-host P2P DMA. The measurements cover one iWARP configuration;
performance on other RDMA transports or staging arrangements requires
further evaluation.

The prototype fixes its device hierarchy before boot and assigns one physical
function per logical endpoint. The reported tests exercise endpoints
individually and do not establish progress, performance isolation, or scaling
under concurrent I/O. Online hotplug, shared-device isolation, live
migration, post-silicon reuse, and alternative driver models remain outside
the demonstrated scope. Other device compositions, timing conditions, and
concurrency levels require additional validation of protocol behavior and
C1--C3 ordering.
