\section{Background and Motivation}
\label{sec:motivation}

\subsection{Real Devices and the Native-Driver Contract}

Full-system validation exercises more than a register specification. A native
driver discovers a device, establishes queues and memory ownership, submits
work, and consumes data and completion state according to a device-specific
protocol. Controller firmware, reset behavior, DMA ordering, and interaction
with the unmodified driver all affect what the system observes. A software
model is useful for early bring-up and fault injection, but its modeled
behavior is an assumption. A physical device contributes an independent
implementation of the controller and its firmware.

Enumeration establishes the device view, but reachability alone cannot
preserve its runtime contract. A driver transfers ownership of work whose
memory references may not be reachable from the assigned physical device.
Relaying its doorbell leaves that address-domain mismatch unresolved.
Likewise, notifying the driver of completion does not make preceding payload
writes visible. Figure~\ref{fig:driver-contract} isolates these two missing
guarantees. A usable contract must prepare reachable work before physical
execution and make data visible before ownership returns to the driver.
The coordination mechanism is developed in Section~\ref{sec:design}.

\subsection{Attachment Coupling and the Integration Tax}

Direct attachment couples the topology and capabilities the DUT discovers to
the physical device and its placement. It also ties device-control semantics
and the DMA path to that attachment. A PCIe fabric can change where a physical
device is reached, but relocation alone neither constructs a different
DUT-visible hierarchy nor translates the device-specific queue and DMA state
expected by the native driver~\cite{li2017composable,lim2024flexforge}. The
distinction matters: physical reachability is only one part of the contract in
Figure~\ref{fig:driver-contract}.

We define the \tax as the incremental hardware and engineering cost of adding a
device type or instance to an FPGA validation platform. It includes
device-specific RTL, configuration state, on-chip buffers, routing pressure, timing
closure risk, and resynthesis effort. Adding a new \emph{type} may require a
different protocol state machine; adding another \emph{instance} still consumes
addressable state and routing capacity. To limit the first cost, \sys keeps
device-specific control semantics in the host software back-end. Another
endpoint still consumes generic FPGA state and route entries; whether that
growth is small enough to matter remains an evaluation question.

\subsection{Design Requirements}

The design must preserve the native-driver contract while allowing the logical
device view to change. An unmodified DUT OS must enumerate a consistent
hierarchy, and later control, data, completion, and interrupt state must remain
consistent despite their different owners. Software mediation must leave room
for a separate payload path. Within provisioned capacity, changing a supported
endpoint should require neither a different DUT interface nor a new bitstream;
the cost of that capacity still needs measurement. \sys targets
system-software and device interaction above the PCIe link, not electrical or
link-layer validation.
