\subsection{Device Presentation and Physical Execution}

Peripheral access involves both the interface presented to the DUT and
the implementation that executes device operations. A \emph{logical device hierarchy}
specifies the endpoints exposed to the DUT and their organization. In this
paper, the \emph{device view} comprises this hierarchy and the behavior
exposed to DUT drivers.

Device models provide the configuration and behavior
needed to construct a device view. Timing-faithful models and modular
simulators support configurable full-system
experiments~\cite{karandikar2018firesim,biancolin2019fased,li2022simbricks}.
Physical peripherals allow the DUT and its software to interact with real
I/O devices, although direct attachment limits the available device
composition to the prototype's physical interfaces.

FPGA prototypes can use physical peripherals for system-level validation. Feng et al.
use real peripherals in an FPGA SoC prototype to test functional correctness
and end-to-end software execution
before tape-out~\cite{feng2018accelerator}. Callanan et al. combine pre-silicon
environments and existing hardware for chip-level verification and integrated
software testing of an I/O-attached SoC~\cite{callanan2011prototyping}.
% <!--ref:feng2018accelerator--><!--anchor:section:5,page:10-->
% <!--ref:callanan2011prototyping--><!--anchor:abstract-->
Physical-device tests provide integration coverage that complements modeled
experiments, although the prototyping interface may alter I/O timing.

Figure~\ref{fig:design-space} compares how peripherals are exposed to DUT software.
\sysprevious~\cite{scope2026fpt} makes borrowed devices reachable through
mapped BARs or split-driver commands. In \sys, the DUT OS enumerates a
software-selected device hierarchy. Host software maintains driver-visible
state for each endpoint and coordinates I/O with its assigned physical
device. Both systems use physical devices and separate
control handling from payload transfer. \sys also provides the configuration
and behavior needed for DUT OS enumeration and native-driver operation.

Device relocation expands the set of reachable resources, but native-driver
operation also depends on the device hierarchy and behavior exposed to
the DUT. A fabric can change physical-device placement without adapting
the driver-visible configuration, queues, or direct memory access (DMA)
state~\cite{li2017composable,lim2024flexforge}.

Extending peripheral support involves protocol adaptation and interface
capacity. A new device type may require protocol-specific logic, whereas
another instance of a supported type consumes configuration state and
routing capacity. Shared I/O services, as in Feniks~\cite{zhang2017feniks},
can reduce repeated implementation work. Driver compatibility remains
a requirement for every presented endpoint.

\subsection{Reachability and the Native-Driver Contract}
\label{sec:native-driver-contract}

Native drivers expect consistent behavior during discovery, configuration,
request submission, DMA, completion, and interrupt handling. We refer to
these requirements as the \emph{native-driver contract}.
Before normal I/O, the DUT OS performs \emph{device enumeration}: its
PCIe bus subsystem discovers the presented functions and reads their
configuration to establish identities and resource mappings. Driver matching
and binding then associate those functions with their native drivers, which
initialize device-specific queues and establish buffer ownership before
submitting work.
Drivers then read completion and interrupt state according to the device
protocol. The presented endpoint must preserve the behavior expected for
supported operations, including reset and memory-ordering requirements.

Access to memory-mapped I/O (MMIO) alone does not satisfy these requirements.
When the DUT and physical device occupy different address domains, forwarding
a submission write can notify the device while the request it references
remains inaccessible. The device must be able to address and observe the
request metadata and required input data before physical submission. On
completion, returned data must be visible in DUT memory before the driver
observes a completion record or interrupt. MMIO forwarding must therefore
be accompanied by address translation and memory-ordering mechanisms for
both request submission and completion.

\subsection{SDN-Inspired Separation of Responsibilities}
\label{sec:sdn-principle}

\sys assigns peripheral configuration, control mediation, and physical
execution to separate components. Software selects the device composition,
a control subsystem maintains driver-visible state and coordinates I/O,
and compatible physical devices execute operations. This division is
inspired by SDN, which separates applications that specify
network behavior, controllers that coordinate resources, and elements that
execute forwarding decisions~\cite{onf2014architecture}.

Figure~\ref{fig:planes} compares SDN's application, controller, and data planes
with peripheral configuration, control mediation, and physical execution
in \sys. A host-side configuration tool selects the supported device
hierarchy and compatible physical-device bindings. The DUT OS and drivers
interact with the resulting device view.

The FPGA front-end and host software back-ends jointly implement control
mediation in \sys. They keep configuration and routes consistent,
prepare device-visible requests before submission, and make returned data
visible to the DUT before publishing completion. These device-protocol
requirements determine how the components coordinate I/O; the SDN analogy
motivates the separation of responsibilities.

\subsection{Requirements for Software-Defined Access}

Software-defined peripheral access must meet two requirements. First,
software must select the logical device hierarchy and compatible
physical-device bindings before enumeration, within the provisioned FPGA
capacity and without changing supported DUT software or the FPGA bitstream.
Advertised behavior must match what the mediation subsystem and assigned
device can implement together. Second, the FPGA front-end and host back-ends
must preserve the driver's ordering requirements for configuration,
submission, DMA, completion, and interrupt handling.

A valid direct DMA path should remain available for payload transfers
without requiring software to copy the data. Its use depends on the same
memory-ordering requirements as a software-mediated path. \sys targets
functional interaction between DUT software and peripherals. Electrical
validation and timing equivalence to direct attachment are outside this scope.
