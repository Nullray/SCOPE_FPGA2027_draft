\subsection{Device Presentation and Physical Execution}

Peripheral access combines two choices: the interface visible to the DUT and
the implementation that executes its work. A \emph{logical device hierarchy}
specifies the presented endpoints and their organization; the \emph{device
view} also includes their driver-visible behavior. Device models construct
that view and implement the corresponding execution behavior. Timing-faithful
models and modular simulation make configurable full-system experiments
tractable~\cite{karandikar2018firesim,biancolin2019fased,li2022simbricks}.
Physical devices instead supply independently implemented I/O behavior for
end-to-end integration tests, but direct attachment ties the discovered
composition to available devices and their placement.

The value of that participation is system-level validation, not simply greater
detail in a device model. Feng et al. use real peripherals in an FPGA SoC
prototype to test functional correctness and end-to-end software execution
before tape-out~\cite{feng2018accelerator}. Callanan et al. combine pre-silicon
environments and existing hardware for chip-level verification and integrated
software testing of an I/O-attached SoC~\cite{callanan2011prototyping}.

% <!--ref:callanan2011prototyping--><!--anchor:abstract-->
These cases motivate testing the DUT's hardware--software interactions with
physical devices alongside modeled experiments. They do not establish that
physical access preserves target-system timing or covers all device behavior.

Figure~\ref{fig:design-space} compares these organizations and the transition
to configurable presentation. \sysprevious makes borrowed physical devices
accessible through adapted DUT software. \sys adds a software-selected
hierarchy whose device view can be consumed by native drivers, while retaining
the borrowing substrate. Both versions retain physical execution and separate
payload movement. Mediation can nevertheless change timing and concurrency,
so physical participation alone does not establish direct-attachment fidelity.

Configurable attachment and configurable presentation therefore solve
different problems. A fabric can change a physical device's placement without
constructing a different DUT-visible hierarchy or adapting the device-specific
queue and direct memory access (DMA) state expected by its
driver~\cite{li2017composable,lim2024flexforge}. Relocation expands the set of
reachable resources, but does not determine the logical device contract that
the DUT can consume.

Extending that contract can also incur hardware cost. We use the \tax to
describe the incremental hardware and integration cost of adding a device type
or instance. A new type may require protocol-specific logic, while another
instance consumes addressable state and routing capacity. Factoring reusable
I/O services out of application logic is one response to this
cost~\cite{zhang2017feniks}. Reuse can limit repeated protocol specialization,
but the capacity cost of additional logical devices remains to be measured.
Neither reuse nor relocation settles whether the selected view is usable by
an unmodified driver.

\subsection{Reachability and the Native-Driver Contract}

A configurable hierarchy is useful only if its endpoints behave coherently to
the driver. The \emph{native-driver contract} extends from discovery and
configuration to runtime submission, DMA, completion, and interrupt handling.
A driver discovers a device, establishes queues and memory ownership, submits
work, and consumes returned state according to the device protocol. Controller
firmware, reset behavior, and memory ordering therefore affect the observations
that must be preserved; a legal hierarchy alone does not supply these semantics.

Figure~\ref{fig:driver-contract} explains why forwarding memory-mapped I/O
(MMIO) is insufficient when the DUT and physical device occupy different address
domains. A submission can reach the device while its published memory
references remain unreachable. Relaying the doorbell does not resolve that
mismatch. At completion, notifying the driver cannot itself make preceding
payload writes visible. The runtime contract therefore requires reachable
published work before physical execution and visible returned data before
completion returns ownership to the driver.

\subsection{Requirements for Software-Defined Access}

Together, the composition and runtime constraints motivate a supported logical
device view that can change independently of physical attachment. Software
should select the presented hierarchy and compatible physical-device assignments before
enumeration, without changing the DUT driver or rebuilding the FPGA within
provisioned capacity. The advertised contract remains bounded by what the
subsystem and assigned device can jointly implement. Configuration, control,
memory ownership, completion, and interrupt state must therefore remain
consistent across their owners.

Maintaining that consistency should not require every payload byte to traverse
the mediation software. The method must separate state adaptation from byte
movement while preserving the required publication order over a valid memory
path. Reusing a generic FPGA interface can shift device-specific semantics into
software, but the state and routing capacity for additional endpoints remain
real costs to be measured. These requirements concern functional interaction
with system software above the device link, not electrical validation or
direct-attachment timing fidelity.
